LLM Evaluation is a very important part of application layer.Each AI based application should have an evaluation layer to make sure that everything is working as expected.

LLM pipelines break every assumption of traditional testing:
- Non-deterministic outputs: Same inputs can produce different outputs making assertions difficult.
- Subjective quality: Evaluating output quality often requires human judgment. Factually output might be correct, but vibes can be off. Correctness is multi-dimensional and can be hard to define.
- Silent failures are common where the LLM replies confidently and convincingly but is actually wrong. This can be dangerous if not caught.
- Many moving parts: LLMs are often part of larger systems with multiple components, making it hard to isolate issues.

Software Testing vs LLM Evaluation:
- Different hardware architectures implement kernels in various ways, leading to different outputs. This makes it hard to have a single "correct" output for testing.
- While trditional software could match spec exactly, LLMs output is often a judgement like tone, safety, relevance, etc. which is hard to define and measure.
- Failures in traditional software were exceptions and wrong values, while LLMs can give fluent wrong answers.
- Traditional software had "assert" statements to check for correctness, but LLMs require more complex evaluation methods.
- Traditional software breaks at specific lines of code, while LLMs can fail anywhere from prompt, tools, retreival, etc.

The three Gulfs - A mental model on why LLMs go wrong:
- Developer, LLM Pipeline, Data.
- Problems can arise in any pair of this system.
- Gulf of Comprehension: Developers may not fully read what the LLM generates, leading to misinterpretation of outputs.
- Gulf of Specification: Developers may not fully specify what they want from the LLM, leading to outputs that don't meet expectations.
- Gulf of Generalization: While the pipeline works on developer's examples, it fails on real-world pipelines.
- Goal of LLMs is to bridge these gulfs by improving comprehension, specification, and generalization through better design, training, and evaluation methods.

Gulf of Comprehension:
- Thousands of traces get generated, developer might read a few.
- Failures hide in unopened traces, leading to a false sense of correctness.
- Intuition is biased.
Bridge: Systematic error analyis on a sampled representative set of traces.

Gulf of Specification:
- Prompts are often underspecified, leading to outputs that don't meet expectations.
- Models fill in gaps with their own assumptions, which may not align with developer's intent.
Bridge: Precise prompts, and explicit definitions of good.

Gulf of Generalization:
- Even a perfect prompt fails on inputs that you haven't seen before.
- Works during development but user's can introduce edge cases like typos, ambiguity, multiple requests, etc.
- Better models might shrink this gulf, but it will never go away.
Bridge: Diverse test datasets, continuous monitoring, and feedback loops to catch edge cases.

The evaluation lifecycle:
- Analyze: Read traces, fins and name failure modes.
- Measure: Build evaluators for each failure mode, and measure how often they occur. Validate them.
- Inprove: Fix tools, prompts, architecture. Verify - no regressions. Repeat the cycle.
This process will need to be carried out by humans since asking an LLM to evaluate itself is not reliable. Humans are needed to define what "good" looks like, and to validate the evaluators.

Defining good: Three ways to score an output:
- Exact match/code checks: Deterministic, fast, free. Can be used for user IDs, dates, etc. but not for subjective outputs.
- LLM-as-a-Judge: A second model scores the output against a rubric. It handles meaning,tone, but is slower and costly.
- Human review: A person rates the output. It can't scale and is generally used to validate the judges.

Public Evaluation benchmarks might not apply to your specific problem statement. A good model might still fail on your use case. It's important to gather the required traces and build the "taxonomy of failure"
for your specific evaluation. Sometimes the public eval data is leaked into the model's pretraining data. This is called "benchmaxing". 

Case Study for Evaluating a LLM: Barista app:
- 3 Agents:
-- Order agent: Accesses get_menu and parse_order tools.
-- Inventory Agent: Uses check_stock tool.
-- Billing Agent: Calculate_price, apply_discount tools.
All agents write to a common state and never directly communicate. This common state is the trace that is used for evaluation.

What is a Trace?
- It's the complete record of one request - a tree of spans.
- Any LLM call, tool call, routing decision, or user input is a span.
- Traces come form production logs, if available, or else syenthetic queries can be generated to create traces.
- Diverse sythetic queries are generated by sampling dimensions - the different ways users interact with the system - then writing a natural query for each combination of dimensions. This is called combinatorial testing.
- A product manager will define dimensions based on their experience and discussions with stakeholders, to create a robust evaluation suite that will differentiate them from lesser experienced folks.
- LLMs can be used to write natural queries for each dimension combination. These queries can be human reviewd and edited to ensure they are realistic and cover edge cases.

LangSmith can be used to generate traces, and it directl itntegrates with LangChain to capture traces from production. It can also be used to analyze traces, and build evaluators for each failure mode.
Evaluation can be done in two modes:
- Interactive: Each request is traced separately.
- Batch Mode: Score against a test dataset, used mainly when the evaluation is automated and doesn't require human review.

Axial Coding: From notes to Taxonomy
- Once you create your notes on various failure modes, it's time to assign terms to them. This is called axial coding. It helps in organizing the failure modes into a taxonomy, which can then be used to build evaluators and measure performance.
- You can group, merge, split - until each failure mode is crisp and clearly defines the scenario.
- We should aim for 8-10 codes: each with a one-line definition, name, and count, which is how many traces from the test set encountred this code.

Understanding Failures: Systemic and Sporadic Issues:
- Once you count the labels, you get a distribution of failure codes across the test set.
- Failures with high counts are mostly systemic issues, which means that there is some bug in the application architecture that's causing this. Usually, fixing these can negate an entire class of failures.
- Less common failures are sporadic issues, which are usually edge cases that can be fixed with better prompts. These require more targeted testing and evaluation to catch, and are often harder to fix.
- Frequency X Impact guides us on which failure modes to prioritize. High frequency and high impact failures should be fixed first, while low frequency and low impact failures can be deprioritized.

Common pitfalls in Error Analysis:
- Don't jump straight to fixes. First gain clarity on the failure modes and their root causes. This will help in building better evaluators and fixing the right issues.
- Don't only rely on the final replies. Look deeper into tool arguments and intermediate steps. This can help in identifying where the failure is occurring and what might be causing it.
- Don't use borrowed or general taxonomies like "Model Hallucinated". Make a list that is personal to your application and its specific failure modes. This will help in building more accurate evaluators and fixing the right issues.
- Don't stop after a single pass. New traces can surface new failure modes, so it's important to continuously analyze and update the taxonomy and evaluators.
- Don't make the teesting completely autonomous, have a human to evaluate the outputs.

From failure modes to Metrics:
- Once you have a clear taxonomy of failure modes, you can build evaluators for each mode.
- Binary Design: Each evaluator returns a binary score - pass or fail. This is simple, easy to implement and provides a deterministic result. Severity scales can be added later if needed.
- Cheapest Oracle Wins: If code can evaluate the failure mode, stick to it.
- Metrics invented without taxonomy measure what is easy, not what fails.
- Sometimes code + lookup can also be used in case a reference is needed.
- LLM-as-a-judge should only be used when the failure mode is subjective and cannot be evaluated with code or lookup.

Anatomy of an LLM as a judge prompt:
- Criterion: One well-scoped failure mode per judge. 
- Define precise pass/fail definitions from your failure mode taxonomy.
- Provide clear few shot examples from human labelled traces, calibrating the decision model boundary.
- Produce structure output with a pass/fail label and a short explanation of the decision as JSON. This can be passed to an observability system for further analysis.

Deigining a judge is like training a classifier but through prompt engineering:
- Train from hte pool of traces coming from which few shot examples are taken.
- Prompts are refined prompt after every edit. The dev examples must never be used inside the prompt.
- The test examples are touched only once after the prompt is frozen. Gives unbiased TPR/TNR.
- Classical Leak: The dev and test samples are used to refine the prompts which inflates the numbers.

How much to trust your judge?
- Two metrics: True Positive Rate (TPR) and True Negative Rate (TNR).
- TPR: Out of all the traces that actually have the failure mode, how many did the judge correctly identify?
- TNR: Out of all the traces that do not have the failure mode, how many did the judge correctly identify?
- A good judge should have high TPR and high TNR, ideally above 90% for both.

Refining the judge - Do's and Don'ts:
- Edit one thing at a time, always re-score on the dev set. after every change.
- Disagreements with human labels should be studied and the Pass/Fail definitions should be refined to reduce ambiguity.
- Pin th ejudge's model version to a specific model to avoid drift in behavior.
- Don't leak dev or test examples into the prompt.
- on't report the dev accuracy as the judge's real accuracy.
- Don't use a single judge to score multiple failure modes. Each judge should be specific to one failure mode to avoid confusion and ensure accurate scoring.

In Agentic AI with tool calling, there are three checkpoints in every tool call cycle:
- Tool selection
- Argument generation
- Output interpretation

Tool selection problems:
- Wrong tool selection
- Selected a tool not in the list (Hallucinating)
- Didn't call a tool when it was needed.
To resolve this, tools must be given distinct names, descriptions and parameters in the prompt.

Argument generation problems:
- Schema/Type violations
- Missing required arguments
- Structurally valid, semantically wrong arguments.
Schema validation + Reference data checks should be conducted for every tool call.

Output interpretation problems:
- Misreading tool output
- Ignores any errors and carries on
- Wrong conclusion despite correct tool output.
To resolve this, judge the agent's next step against the tool result in the trace.

The spectrum of agency - deciding how much initiative an agent should take:
- Low Agency: The LLM should ask efficient questions to the user and follow their instructions. This is suitable for applications where the user wants to have full control over the process.
- Medium Agency: The LLM should take some initiative, but still ask for confirmation from the user for major activities.
- High Agency: The LLM should take full initiative and make decisions on behalf of the user. This is suitable for applications where the user wants to delegate tasks to the LLM and trust its judgment.
The agency level is a design decision and is a benchmark for evaluation.

Production Monitoring and Guardrails:
- Monitoring is mostly async.
- Sample 1-5% of production traces for evaluation.
- Run 5-7 Evaluators, code checks + validated judges.
- Alert when an interval bound crosses a threshold.
- Guardrails are mostly sync.
- These run inside the request, fast, code-based, low false positives.
- Includes schema validation, PII, blocklists, price sanity bounds.
- On trigger, the request can be rejected, retried, or encounter fallback.
